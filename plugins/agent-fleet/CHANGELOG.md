# Changelog

## Unreleased

- Members run in Claude Code only again: the runner for other agent CLIs (harness profiles, `fleet run`, `fleet harness`, `fleet halt`, the `onboard-harness` skill) is gone.
- Auto effort: a member keeps its model, but works each ticket at the effort the ticket needs — its `Effort:` (set with `--effort` on `fleet ticket set`), else its severity around the member's planned effort (critical one step up, high at the plan, medium one down, low two down). `fleet ticket set` says the owner's effort when a ticket is assigned or started; `fleet status` lists the desktop members to switch (`effort.switch`), which the lead's check switches with `set_session_effort` at a ticket's start — with a clear when one is due, since the switch re-writes the member's context to the cache once — and records with `fleet effort <id> <level>`. On by default for new plans (`autoEffort`). A plan may give a member `"model": "auto"` and `"effort": "auto"`: the role's effort and model, Opus at `xhigh` or `max`.

## 0.9.0 — 2026-11-03

- Discussions read like a conversation with minutes: the protocol and `discuss-and-decide` ask each thread post to open with its point and whom it concerns (`@id`), with the evidence after it, in the mission's language; the opener to end with a recommendation and a default; nobody to act on a point before it is decided; and the `Decision:` line to be a plain sentence of what was chosen and who does what, since the dashboard shows it on the discussion.

- Channel posts read cleaner on the dashboard: a member's id inside a path or a branch name (`reports/po.md`, `claude/…-dev-app-…`) is no longer a mention, `**bold**` shows bold, commit hashes are set back in a quiet short form (the full hash on hover), and a post that opens with its author's own id ("po: …" by po) drops it.
- One channel for the team, as in a Teams channel: the dashboard's Discussions panel is gone and each discussion shows in the team channel as a conversation, where it last moved — who leads it, its state and deadline, its ticket, the question (the thread's `## Context`), the decision or who is still to answer, then its last reply with "N more replies" to open them all. Open discussions are pinned under the channel's header and jump to their conversation. The server now reads a thread's context. Vietnamese labels read more naturally ("Chủ dự án", "Mở rộng", "Sao chép").
- Team channel posts read like a team chat, not a log: the protocol, the briefs, the agents and `team-communication` ask for one or two plain sentences in the mission's language with its accents, `@id` for whom a post concerns, no opening with one's own id, and the commits, test counts and command output left to the ticket's Log, with before-and-after examples. A ticket moving is not news there unless someone must act on it now.

## 0.7.0 — 2026-11-01

- A redesigned header: a top bar with the brand and the mission's name, a quiet live dot and the clock with the time left, and compact search, language ("VI") and theme buttons; under it, the mission's phases across the whole width — each as long as it lasts, the done ones tinted, the current one outlined in gold and filled as far as it has gone. A short phase drops its times, then its name (its tooltip keeps both), so labels no longer run into each other on a narrow screen; on a phone the mission's name stays readable.
- The dashboard is set in Geist and Geist Mono, bundled with it (no Google Fonts request; Latin, Vietnamese and Cyrillic, each loaded only when a page needs it). Mono is kept for what reads as code — ticket ids, commits, branches, paths, commands, the clock — and names, labels, badges and figures are in Geist, with tabular figures throughout. KPI numbers are firmer (500, not 300), nothing is smaller than 11px, and Japanese, Korean and Chinese each name their own system fonts after Geist, so shared characters take the right form and a line keeps one height.
- The heart mascot is gone: reviewers are a pink cloud in sunglasses, and a fleet whose plan still names the heart gets the cloud.
- Richer Code & infra and Report tabs. **Code & infra**: figures for branches, commits integrated, lines changed, merges ready and the base branch; the next integration round — each merge with its tickets, packages, named message and a button that copies the command, then what is blocked, already in, missing or unticketed, and whether the full suite is needed; the pre-flight checks with the services; a commit timeline (one lane per branch over the mission's phases, a dot per commit, filled once integrated, commits from before the start in a gutter); branches that open onto their commits, each linked to its tickets; and hotspots — the packages several members change, and changes outside a member's area. **Report**: a mission summary (tickets, done, verified, parked, reopened, median cycle, tokens, an outcome bar) with the final report and a button that copies a Markdown summary of it all; a table per member (done/owned, verified for others, reopens, commits, tokens per done ticket, report written or missing); every ticket's outcome, filtered by group or text, sorted by any column, copied as Markdown or downloaded as CSV; open risks; and the decisions taken in threads. Both tabs work on a phone and in both themes, in all five languages.
- The dashboard server reads more for the Code & infra tab: each branch's lines and files changed over the base, by package, and — in a child process, so the stream never stalls — the next integration round (`fleet integrate`, every 30 s) and the pre-flight checks (`fleet doctor`, every 2 min), both only while someone watches.
- Each member has an inbox on the board, because a SendMessage to a busy session waits until its turn ends and a compaction can lose it. `fleet send <from> <to>[,<to>|all] <text>` appends to `inbox/<id>.md`; the message waits there until `fleet ack <id> <n>|all`, and `fleet inbox <id> [--all]` lists it. The prompt hook shows a member its unread messages on every prompt it gets, with the command that acknowledges them, and a resume note counts them. `fleet status` reports unread messages per member with the oldest one's age, and the lead's recurring check rings again for any over 10 minutes. Both files only grow, so senders and the reader never overwrite each other. The protocol and `team-communication` use the inbox for one-member messages and keep SendMessage as the doorbell.
- `fleet integrate [--json]` does the git archaeology of an integration round, read-only: the `fixed` tickets in merge order, each with its commit, the packages it touches, and the exact `git merge --no-ff … -m "merge(<scope>): …" -m "Tickets: …"` command. A fix that another fix brings along merges with it; a fix with unready work below it (a deferred ticket's commit) is blocked, with whom to ask; fixes already in the integration branch, fixes with no commit and commits with no ticket are named; and it says whether the round touches shared code and needs the full suite. `integrate-branches` starts each round with it.
- Tickets move by the protocol, not by hand: `fleet ticket set <ID> <status> --by <id> [--note …] [--fix …] [--owner …] [--verifier …] [--decision …]` refuses a move that skips a step, a move that is not the member's (only the verifier verifies, never the owner or crew; integration is the release manager's; triage the product owner's; the lead may make any move but verify) and a move without its evidence (`fixed` needs `Fix:` and a note with the command and counts; `assigned` an owner and a verifier; `triaged` a severity, a decision and acceptance criteria; parked statuses a reason). It sets the fields it is given, writes the `Status:` word and the Log line with the clock's time, and says when a member takes a second ticket in progress. `--force` is the lead's escape hatch and is logged. `fleet ticket list [--status …] [--owner …]` lists the board. The protocol and briefs tell members to use it instead of editing `- Status:`.
- Another round with the same team: `fleet clone --name <name> [--hours N] [--goal …] [--carry …] [--dry-run]`, offered by `/agent-fleet:new` when a fleet ran here before and by `/agent-fleet:wrap-up` when tickets are left. It keeps the members and the budget, drops what the last round recorded (sessions, transcripts, windows), starts a fresh board from now with the phases scaled to the new length, renames a named integration branch, and carries the open tickets over as `new` under `CO-…` ids, so they never collide with the ids members number from 001 again; each says in its Log where it came from. The last round's board is left as it was.
- `fleet doctor` checks a fleet before it launches, and `/agent-fleet:launch` runs it first: Node, the plugin version against the fleet's, the base branch, uncommitted changes worktrees will not see, the git-ignored env files a worktree will not have, the variables turbo's strict env mode drops (the cause of a real run's API suite skipping itself while reported green), briefs and installed agents, the `claude` CLI for headless members, the current fleet and the dashboard's port. `✗` must be fixed, `!` is read to the user. Briefs of members in worktrees say to copy the env files in before running tests.
- A fleet knows which plugin wrote it. Every write (`fleet init`, `add`, `extend`) stamps `plugin.version` in `fleet.json`, since the briefs it writes call that version's CLI. A session on an older plugin is told to update and restart — by the session-start hook and by a warning on every fleet command — instead of running a protocol that names commands it does not have. `fleet version` prints both versions.

## 0.6.0 — 2026-11-01

- A more professional logo: one flat arrow in three layers — the lead at its gold tip, the members behind it in silver and slate — on a dark tile, replacing the mascot trio. It is still, with no blinking or twinkle, in the dashboard header, the loading screen, the favicon and the README.
- Give a running fleet more time: `/agent-fleet:extend` ("2 hours", "until 18:00") shows the new end, the phases, the members whose window moves and the tokens the fleet is now expected to write against the limit, then on a yes runs `fleet extend --hours N | --to T [--dry-run]`. The phase in progress grows (the work phase during the start-up) and the later ones (freeze, reports) move with the end, keeping their length; windows that ended with the fleet move too. It rewrites `fleet.json`, the board's README (end and timeline), every brief and every agent — tickets, reports, roster and session ids kept — notes it in `NOTICES.md`, posts it on the team channel, and prints the one line the lead sends to each running member. No more editing `endAt`, the phases and the timeline by hand while the briefs still say the old end.
- Every member gets its own branch. `fleet launch-plan` named branches `<slug>-<id>` cut to 24 characters, so a slug of 24 characters or more (`kintsugi-backlog-sweep-3`) gave every member the same branch. The id is now never cut: when `<slug>-<id>` is too long, the slug's initials stand for it (`kbs3-dev-core`). `fleet spawn` names worktrees the same way.
- `fleet init` no longer overwrites a fleet behind the lead's back. It refuses, unless given `--force`, to rewrite a fleet of the same slug whose members have started (its `fleet.json` would lose their session ids and times), and to make a new fleet current while another is still running (fleet commands and the dashboard would stop following it). `/agent-fleet:new` puts the choice to the user.
- The dashboard comes back on the port it had. `fleet dashboard` tries the port in `dashboard.json` first, and `fleet stop` keeps it there, so a dashboard that died with the lead's session no longer moves from 4600 to 4603 when it is started again. The lead's recurring check runs `fleet dashboard` to bring it back.
- `integrate-branches` closes the gaps a real run hit:
  - Before the baseline, make sure the tests can run in the worktree (its `.env`, the services, variables a task runner such as turbo drops). The baseline records the exact commands and the passed, failed and skipped counts per suite.
  - Every round compares those counts with the baseline: more tests skipped is red until explained and run, so a suite that skipped itself is no longer reported green. A test that times out is re-run alone once before the merge is called red.
  - Merges carry a message that says what came in, `merge(<scope>): … ` with a `Tickets:` line, never git's default — no more rewriting history to rename them.
  - Only the commits of `fixed` tickets are merged: a branch with unready work below the ready commit goes back to its owner to split.
  - Checks are scoped: the touched packages and their dependents after each merge, the full suite once a round only when shared code changed, and always at the freeze.
- Skipped is not passed: `verify-before-done` asks for the exact command with its passed, failed and skipped counts, and treats tests that prove the claim being skipped as unproven. `review-change` runs the ticket's tests and repro instead of reading the diff alone, and the product owner (`triage-tickets`) re-runs the verifier's main command before accepting.
- No more stacked commits: the protocol (rule 2) and the developer's duties say each ticket's commit must merge on its own — a ticket is never built on a commit whose ticket is not yet `integrated`; the next one starts on a new branch from the integration branch instead. Nobody works on a `deferred`, `wont-fix` or `duplicate` ticket.
- The planner and `/agent-fleet:new` propose a release manager on Sonnet + medium whenever more than one builder commits, small teams included, instead of leaving integration to the lead.

## 0.5.0 — 2026-11-01

- Context kept lean to save tokens. Every model call re-reads a member's whole context, so a member that carries its last ticket into the next pays for it on every step. The plan's new `context.compactAt` (100k tokens by default, 100k to 1M, 0 for off) is the size members are kept under:
  - Subagents compact there on their own (`autoCompactWindow` in each generated agent), and so do headless members (`fleet spawn` sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW`).
  - A desktop session cannot be compacted from outside, so the lead clears it. `fleet status` lists the desktop members that sit idle over the limit (`context.clear`, with each member's context size and tickets in progress). The lead's check clears each one and wakes it with `fleet resume <id>`: who it is, its brief, its open tickets with the one in progress first, and where the team is.
  - Every brief and resume note starts with a `Fleet member: <slug>/<id>` line. The prompt hook records each member's sessions from it (`.fleet/<slug>/sessions/<id>.jsonl`), and after a compaction the session-start hook gives that member its resume note.
  - The protocol (rule 8), briefs and agents say the board is the members' memory: when a member finishes a ticket, and before it ends a turn, the ticket's Log says where it is and what comes next, so a clear loses nothing.
- The dashboard and `fleet status` follow a member across all its transcripts: the ones the hook recorded, plus every one with its title or description, summed oldest first, with the newest as the member's live state. A member cleared with `/clear` keeps its tokens on the budget, where before only its newest transcript counted.
- Add members while the fleet works: `/agent-fleet:add` proposes a member the fleet needs (role, area, model, effort), shows its estimated tokens against the limit, and launches it. Under it, `fleet add <member.json> [--dry-run]` adds one member or several to `fleet.json` — the others, their session ids and the fleet's times kept — writes the new brief and agent, adds the roster rows and the protocol's roster, notes it in `NOTICES.md`, posts a heads-up on the team channel, and prints what to launch. A new member works from now to the end unless given a window; a second lead, a used id or an ended fleet are refused, and an area another builder owns is a warning. The dashboard picks the member up by itself.
- Re-running `fleet init` adds a row to `ROSTER.md` for a member it lacks, instead of leaving the roster as it was.
- A ticket is filed at its first Log line when that is earlier than its file's birth time, which moves whenever an editor saves by replacing the file (Windows). Tickets no longer look fixed before they were filed, the burn-up's created line no longer runs under the fixed one, and the median cycle time is no longer 0 s.
- Verifiers are matched by whole id, as owners are: `qa` no longer counts the tickets `qa2` verifies ("fixes to verify", "verified n/m"). Owners in the member drawer and the cheer counts are matched the same way (`dev` no longer matches `dev-api`).
- Integrated commits are counted against a real branch: the plan's new `repo.integration`, else the branch the release manager recorded in the roster. `/agent-fleet:new` names it when there is no release manager. Without one, the dashboard shows "no integration branch set yet" instead of a misleading 0, and no longer runs `git rev-list <base>..undefined`. The integration branch is read even without a slash in its name, and its commits no longer double the Code tab's count.
- `fleet init` writes the first notice on the local clock, like every other board line, not in UTC.
- Mascots redesigned: seven new animal shapes (cat, bunny, bear, chick, owl, ghost, mochi) with ears that twitch, a tuft that bobs and a ghost that floats; every mascot has little feet, shinier eyes and rosier cheeks, the animals a lighter tummy, a muzzle, whiskers or a beak. Roles get the new animals (the lead a chick with a crown, testers bunnies, the architect an owl…), and fleets planned before keep their role's new look. Members who would look the same — two developers, two testers — each get a colour of their own, as far as can be from the others, and a hair clip (a flower, a star, a leaf, a heart); members of custom roles get a shape and colour nobody else has.
- A logo: a chick (the lead) with a cat and a bunny peeking from behind it, on a dark tile with a star — in the dashboard header (its eyes blink, the star twinkles), the loading screen, the browser tab (`favicon.svg`) and the README. The page title before the fleet loads is "Agent Fleet", not "Kintsugi Fleet".

## 0.4.0 — 2026-11-01

- The dashboard re-reads `fleet.json` when it changes — members added, removed or renamed, a session id recorded by `fleet spawn`, the window, the token limit, the board folder — without a restart; a file caught mid-write is skipped and the last good plan kept. The port is read only at start.
- Members in worktrees: the protocol has a "Writing to the board from a worktree" section — the board is in the main checkout and not in git, so read and write it only by its absolute path, never create or commit board files in the worktree, write ticket paths relative to the repository root, and tell the lead when a write is refused. Briefs, agents and the protocol give absolute board paths for every grep, and the exact `fleet roster … --fleet <dir>` command to record a member's worktree and branch (`--fleet` may now come after the pairs).
- Tickets no longer jump from `assigned` to `fixed`: nothing told a builder to set `in-progress`, so none did. The protocol now has a table of who moves each status and when (the owner sets `in-progress` the moment they start; never skip a status; a ticket put down goes back to `assigned`), and the developer and writer roles, `plan-ticket`, every generated agent and every brief say so.
- `fleet status` reads a ticket's status as the dashboard does: `In progress` counts as `in-progress`, not `In`.
- Every status audited. The protocol's table now covers all of them — `new` through `verified`, `reopened` (who may reopen, and the owner's way back through `in-progress`) and the parked `deferred`, `wont-fix`, `duplicate` — and says the `Status:` line holds the status word only, and that Log times come from the clock (`date +%H:%M`), appended oldest first. `triage-tickets`, `respond-to-review` and `verify-before-done` agree with it.
- Status parsing: only the status word counts, so `duplicate → N-019`, `fixed — dev-api @ 7f3a` or `deferred to next sweep` no longer show up as unknown stages; `won't fix`, `on hold` and the like stay one status.
- A Log time later than the ticket file's last save (a member guessing the clock) is read as that save, so it no longer hides a stale ticket or skews time in stage. A reopened ticket's fix time is the owner's last fix, not the first.
- Status moves are saved beside the history (`transitions.json`): a dashboard restart keeps each ticket's time in stage, and a move made while it was down is recorded at the ticket file's change. Up to 1000 moves are kept (was 300).
- A Windows checkout (`core.autocrlf`) no longer breaks generated files: templates are read with LF line ends, so agents keep valid front matter and briefs and the protocol carry no stray CR.
- Team channel: `CHANNEL.md` on the board for short news everyone needs now (heads-up, ask, answer, fyi), one line per post. `fleet say <member|owner> <kind> <text>` posts with the clock's time and one append per post, so posts at the same moment never erase each other. The protocol, briefs and agents say when to use it (and when a ticket, thread or direct message is the place instead), `team-communication` lists it, and members broadcast there instead of in `NOTICES.md`, which stays the lead's.
- The dashboard server reads the team channel: its last 200 posts with their kinds, on the mission's clock (a guessed future time read as the file's save, as in tickets), and serves `CHANNEL.md` to the document drawer.
- Dashboard: the team channel as a chat channel — messages grouped by member, time dividers after a quiet stretch, kind badges (a heads-up stands out), `code`, ticket ids that open the ticket and members' ids as mentions, who posted in the last half hour, a "new" pill when you have scrolled up, and a composer that shows (and copies) the `fleet say` command. It opens large in a dialog; channel posts also appear in the live feed. In the side column of Overview (once there are posts) and Team.
- `fleet dashboard` prints the URL on a line of its own (a link in a terminal and in Claude's reply), says whether it started or was already running and which port it moved to, and how to stop it; `--json` keeps the machine form. The commands tell Claude to give the URL as a clickable link, never only the port. Finding a dashboard already running no longer crashes Node on Windows (a kept-alive fetch socket at exit).

## 0.3.0 — 2026-11-01

- The account's home folder never leaves the server: every state, patch and board document the dashboard receives shows it as `~`, in all its spellings (Windows, POSIX, MSYS and Claude Code's dashed transcript-folder names).
- A quiet fleet no longer looks disconnected: the server pings every 15 s, since patches only flow on changes.
- A ticket's verified time is the last Log line that says so (earlier mentions are pre-checks), so cycle times are right.
- Marketplace and plugin manifests point at `github.com/khuonghung/claude-agent-fleet`; install from GitHub with `claude plugin marketplace add khuonghung/claude-agent-fleet`.
- Skills: `decompose-goal`, `write-ticket`, `triage-tickets`, `dispatch-work`, `plan-ticket`, `verify-before-done`, `review-change`, `integrate-branches`, `status-report`. The role catalog maps roles to skills; each generated agent and brief lists its skills and when to use them; a plan may override a member's list (validated).
- A ticket opens in a centred modal: its place in the flow as a stepper, time in the current stage, the acceptance criteria as a checklist, the problem and the rest of its text, one activity timeline (log, status moves, discussion posts, commits), the people on it, its facts, and its references — the discussion, the commits that name it or its fix, the tickets it mentions and that mention it (opened in place, with Back), the files it points at (copied on click); ↑ ↓ walk the board. The server extracts each ticket's mentions and files.
- No coloured edge borders anywhere (modal top, member and org cards, ticket cards, list rows, quotes): severity shows in its badge or a small dot, the squad as a dot before the member's title.
- Ticket flow reworked: a pipeline strip (each stage as wide as its share; a click focuses it), flow metrics (in flight, awaiting verification, verified, median cycle time, verified in the last hour, stale), filters by severity, owner and "needs attention" kept per viewer, a sortable list view beside the board. On the board, empty stages fold into narrow rails and a lone populated stage spreads its cards across the width; long columns show 12 and expand; open work is ordered by urgency, finished work by recency. Cards show the owner, crew and verifier, time in the current stage, a stale warning per status, the discussion and the fix. Owners are matched by whole ids, so `dev` no longer matches `dev-api`.
- Working together: board **threads** (`threads/<topic>.md`: owner who decides, members who must answer, a deadline, typed posts, the decision) with direct messages only as the doorbell; shared tickets name their `Crew:`. New skills `team-communication`, `discuss-and-decide`, `swarm-ticket` (split behind a contract, builder + tester, driver + navigator, parallel investigation, multi-reviewer), `investigate-bug` (root cause first; competing hypotheses across members) and `respond-to-review`; every role gets `team-communication`. The dashboard shows discussions (who is still to answer, the decision), puts their posts in the live feed, and flags a discussion past its deadline.
- The skills were rewritten after reading their sources in full: report statuses and rulings in `dispatch-work`, consumes/produces interfaces and checkable steps in `plan-ticket`, the gate and claim-evidence table in `verify-before-done`, review dimensions, severity calibration and deduplication in `review-change`, split strategies and shallow graphs in `decompose-goal`.
- Token limit is the user's choice: `/agent-fleet:new` (and `launch`, for a plan without one) always asks whether to limit output tokens — at the suggested budget, another amount, or not at all — and what happens at the limit (`budget.onLimit`: `warn`, `wrap-up` or `stop`; a warning at `budget.warnAt`, 80% by default). `fleet status` reports tokens used against the limit; the lead's recurring check acts on it once; the dashboard shows the limit, its action and a near-limit alert.
- Models are named exactly everywhere: the catalog, `/agent-fleet:new` and the dashboard say `Claude Opus 5.5` (`claude-opus-5-5`), not a bare alias.
- Token estimate from measured rates: `fleet estimate` gives each member's expected output tokens (model and squad rate × effort × active share of its window), a range and a suggested budget. Output tokens are now counted once per model message (Claude Code writes one line per content block with the same message id; they were counted up to 3–4 times).
- Dashboard: its own controls instead of native ones — dropdowns, tabs and segmented controls with a sliding indicator, a search field with `/`, a command palette (Ctrl/⌘ K), toasts for ticket and member events, animated numbers, FLIP motion for tickets that change column, a pointer spotlight and lift on cards, member cards and a phase stepper in the Org chart, the reporting line lit on hover, a projected end-of-mission token use on the budget meter.
- Mascots come alive: a smooth, lit body (soft highlight and belly shade, a thin outline, a soft ground shadow) instead of the jagged fur filter; cheeks and a mouth that show the mood; eyes that blink on each mascot's own rhythm and follow the pointer (one shared listener), or look around when it rests; per state, hopping with squash and stretch and sparks (running a tool), a thought bubble with typing dots (thinking), a happy wiggle (replied), breathing (waiting), dozing with Zzz (silent); they perk up on hover, squash with a heart when clicked, and jump with confetti when a ticket they own or verify is verified. Silent members now doze (the state was renamed and they had stopped).
- Server: patches instead of the whole state each second (the board alone is ~300 kB); git and probes read only while a client is connected; git reads in parallel; hashed assets cached; a stricter static-path check.
- Examples and samples are in English.

## 0.1.0 — 2026-11-01
