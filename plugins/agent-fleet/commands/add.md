description: Add a member to the running agent fleet — role, specialty, area, model, effort — write its brief and agent, and launch it
argument-hint: "[who to add, e.g. \"a tester for the portal\"]"
---

Add a member to the current agent fleet while it works. The fleet CLI is `node "${CLAUDE_PLUGIN_ROOT}/scripts/fleet.mjs"` (call it `fleet` below); run it from the project root. Speak the user's language.

1. Run `fleet status --json`. With no fleet, point the user to `/agent-fleet:new` and stop; with no time left (`minutesLeft` 0), say a member cannot join a fleet that has ended and stop.
2. Read `.fleet/<slug>/fleet.json` (members, their `reportsTo`, `owns`, `launch`), `BOARD.md` and the open tickets, so you propose a member the fleet needs: who is overloaded, which area has no owner, which tickets wait. Run `fleet catalog` for the roles, models and efforts.
3. Starting from `$ARGUMENTS`, propose the new member in one round (AskUserQuestion when available): `id` (kebab-case, not used yet), role, who it reports to, `specialty` (one or two sentences in this project's words), `owns` (the paths it changes — not another builder's, unless an area is handed over), model by full name and id with effort, and how it runs (`launch`, default the fleet's). A fleet has one lead: never add another. Its window runs from now to the fleet's end unless the user gives one (`window: { from, to }`, ISO times).
4. Write the member to `.fleet/add.json` (one object, or an array to add several) and run `fleet add .fleet/add.json --dry-run`. Fix every problem it lists. Show the user the completed member, its estimated output tokens (`estimate`), and the token limit from step 1 — offer to raise `budget.outputTokens` in `fleet.json` when the new member would take the fleet past it. Read each line of `warnings` (an area another member owns) to the user: either change `owns`, or agree the handover — then tell the member who gives the area up, and change their `owns` in `fleet.json` too.
5. On the user's go-ahead, run `fleet add .fleet/add.json`. It adds the member to `fleet.json` (everyone else, their session ids and the fleet's times kept), writes its brief and agent, adds its row to `ROSTER.md` and the protocol's roster, notes it in `NOTICES.md` and posts a heads-up on the team channel. The dashboard picks it up by itself.
6. Launch it from the `launch` entries the command printed, exactly as `/agent-fleet:launch` step 3 says for its `launch` kind. A `subagent` member's agent is new to this session, so use `general-purpose` with its agent file and brief.
7. Tell its manager (SendMessage to their session id or name) that the member joined, what it owns and to give it its first tickets; reassign tickets of the area it took over. Give the user a one-line summary and the dashboard link.
